# 재고 차감 락 구간 리팩토링

## 목적

동일 상품의 재고 차감 요청은 재고 수량 정합성을 위해 순차 처리해야 합니다. 병렬 실행으로 처리량을 높이는 대신, 재고 정합성 보호에 필요하지 않은 작업을 분산 락 밖으로 이동하여 요청당 락 점유시간을 줄입니다.

재고 소프트 삭제 필터를 동일하게 적용한 두 코드 버전을 VU 200, 60초 조건으로 각각 3회 측정한 결과는 다음과 같습니다.

| 지표 | 리팩토링 전 | 리팩토링 후 | 변화 |
|---|---:|---:|---:|
| 성공 TPS | 151.60 | 166.53 | **9.85% 증가** |
| API 평균 응답시간 | 1334.35ms | 1223.27ms | **8.32% 감소** |
| API p95 | 2058.76ms | 2028.40ms | 1.47% 감소 |
| API p99 | 2762.12ms | 2511.86ms | **9.06% 감소** |
| 평균 락 대기시간 | 1325.78ms | 55.12ms | **95.84% 감소** |
| 평균 락 점유시간 | 6.10ms | 5.46ms | **10.58% 감소** |

위 값은 지표별 3회 중앙값입니다. 평균 락 대기시간 감소에는 상품 조회가 락 측정 구간 앞으로 이동한 영향이 포함되므로, 사용자 관점의 성능 개선은 API 응답시간과 TPS를 기준으로 판단합니다.

## 변경 전

`StockDecreaseProcessor`가 상품 조회, 재고 조회·차감, 응답 DTO 생성을 모두 담당했고 Processor 전체가 분산 락 안에서 실행됐습니다.

```text
락 획득
→ 트랜잭션 시작
→ 상품 조회
→ 재고 조회
→ 재고 차감
→ StockResult 생성
→ 트랜잭션 커밋
→ 락 해제
```

상품 조회와 응답 생성은 재고 수량의 동시성 제어에 직접 필요하지 않지만 락 점유시간에 포함됐습니다.

## 변경 후

상품 조회와 상품명 확보는 락 획득 전에 수행하고, 응답 DTO는 락 해제 후 생성합니다. `StockDecreaseProcessor`에는 활성 재고 조회와 차감 트랜잭션만 남깁니다.

```text
상품 조회 및 상품명 확보
→ 락 획득
→ 트랜잭션 시작
→ 활성 재고 조회
→ 재고 차감
→ 트랜잭션 커밋
→ 락 해제
→ StockResult 생성
```

재고 조회와 Redis 락 키는 계속 `productId`를 기준으로 합니다. `productName`은 현재 재고 API 응답 계약을 유지하기 위한 표시 정보이며 재고를 찾거나 차감하는 조건으로 사용하지 않습니다.

## 트랜잭션과 락 순서

재고 차감 트랜잭션은 별도 Spring Bean인 `StockDecreaseProcessor`의 `@Transactional` 메서드에서 시작됩니다. `StockLockManager`가 Processor를 호출하므로 Spring 트랜잭션 프록시가 적용됩니다.

```text
StockLockManager 락 획득
→ StockDecreaseProcessor 프록시 호출
→ 트랜잭션 시작
→ 재고 차감
→ 트랜잭션 커밋
→ Processor 반환
→ 락 해제
```

락을 트랜잭션보다 먼저 획득하고 커밋이 끝난 뒤 해제하는 순서를 유지해야 합니다. 커밋 전에 락을 해제하면 다음 요청이 아직 반영되지 않은 재고를 조회할 수 있어 정합성이 깨질 수 있습니다.

Processor가 반환한 `Stock`은 트랜잭션 종료 후 Service에서 즉시 `StockResult`로 변환합니다. `Stock`에는 지연 로딩 연관관계가 없고 기본 필드만 읽으며, 락 밖에서 추가 변경하거나 저장하지 않습니다.

## 상품 수정·삭제 경합

상품 수정과 삭제 API는 재고 차감 Redis 락을 사용하지 않습니다. 따라서 상품 조회가 락 안에 있던 기존 구조에서도 상품 변경과 재고 차감 사이에 강한 일관성은 보장되지 않았습니다.

상품 조회를 락 밖으로 이동하면 상품 조회 후 재고 차감까지의 간격에 락 대기시간이 추가됩니다. 기존에 존재하던 경합 가능 구간이 길어지는 트레이드오프가 있습니다.

### 상품명 수정

상품 조회 후 이름이 변경되면 재고 차감 응답에 조회 시점의 상품명이 포함될 수 있습니다. 재고 수량은 상품 ID 기준 락으로 보호되므로 영향을 받지 않습니다. 주문 서비스의 재고 차감 Feign Client는 반환 타입이 `void`이므로 응답 본문의 상품명을 소비하지 않습니다.

### 상품 소프트 삭제

상품 조회가 성공한 직후 상품이 소프트 삭제되면 재고 차감이 성공할 수 있습니다. 이 경합은 리팩토링 전에도 존재했고, 리팩토링 후에는 락 대기시간만큼 가능 구간이 길어집니다.

삭제 진행 중인 상품의 주문을 완전히 막으려면 판매 중지, 진행 중 주문 처리 완료 확인, 상품 삭제 순서와 같은 업무 정책이 필요합니다. 이번 리팩토링은 재고 수량 정합성과 락 점유시간 개선에 범위를 한정하고 상품 생명주기와 주문의 조율은 별도 문제로 남깁니다.

## 재고 소프트 삭제 필터

재고 조회는 `deletedAt IS NULL` 조건을 사용하여 활성 재고만 반환하도록 변경했습니다.

```text
StockRepository.findByProductIdNotDeleted(productId)
→ JpaStockRepository.findByProductIdAndDeletedAtIsNull(productId)
```

이 필터는 소프트 삭제된 `p_stock` 행이 조회·차감되는 문제를 방지합니다. 상품 삭제는 현재 `p_product`만 소프트 삭제하고 `p_stock`을 삭제하지 않으므로, 이 필터가 상품 삭제와 재고 차감의 경합을 해결하지는 않습니다.

## 검증 전략

| 검증 | 확인 내용 |
|---|---|
| `StockServiceImplUnitTest` | 상품 조회가 락보다 먼저 실행되고, 상품이 없으면 락을 호출하지 않는지 확인 |
| `StockServiceImplTest` | 실제 MySQL·Redis 환경에서 단일 차감과 소프트 삭제 재고 제외 확인 |
| `StockConcurrencyTest` | 100개 동시 차감 후 재고 수량 정합성 확인 |
| Micrometer Timer | 평균 락 대기시간과 평균 락 점유시간 측정 |
| k6 compare | API 평균·p95·p99, 성공 TPS, 실패 건수 측정 |

기존 baseline은 재고 소프트 삭제 필터를 적용하기 전에 측정했습니다. 필터는 재고 조회 SQL에 `deleted_at IS NULL` 조건을 추가하므로 기존 baseline과 리팩토링 후 결과를 바로 비교하면 조회 조건 변경과 락 구간 변경 효과가 섞입니다.

락 구간 변경 효과만 비교하려면 다음 두 코드 버전을 같은 세션에서 측정해야 합니다.

```text
before: 재고 삭제 필터 적용 후, 락 구간 변경 전 커밋 e15ae40
after:  재고 삭제 필터와 락 구간 변경이 모두 적용된 커밋 5b4848c
```

두 버전 모두 VU 200, 60초 조건으로 3회 측정하고 지표별 중앙값을 사용했습니다. 동일한 시드, 락 정책, MySQL 스키마, Redis DB를 사용하여 비교에서 달라지는 변수를 락 구간 리팩토링으로 제한했습니다.

세부 실행값, 유효성 검증과 해석은 [재고 차감 분산 락 측정 결과](scenario1-lock-result.md)에 기록합니다.
