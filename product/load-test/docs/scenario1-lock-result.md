# 시나리오 1: 재고 차감 분산 락 측정 결과

## 목적

동일 상품에 재고 차감 요청이 집중되는 상황에서 API 성능과 분산 락 내부 지표를 함께 측정합니다. 재고 소프트 삭제 필터를 동일하게 적용한 두 코드 버전을 비교하여 락 점유 구간 변경의 효과만 확인합니다.

### 재고 소프트 삭제 필터 적용 전후 참고 비교

기존 baseline과 현재 통제 비교 결과를 함께 배치하면 다음과 같은 차이가 관찰됩니다.

| 단계 | 코드 | 재고 소프트 삭제 필터 | 락 구간 | 성공 TPS | API 평균 | API p95 | API p99 | 평균 락 대기 | 평균 락 점유 |
|---|---|---|---|---:|---:|---:|---:|---:|---:|
| 기존 baseline | `b4ef400` | 미적용 | 기존 | 224.25 | 897.06ms | 1218.23ms | 1499.64ms | 891.39ms | 4.15ms |
| 통제 비교 전 | `e15ae40` | 적용 | 기존 | 151.60 | 1334.35ms | 2058.76ms | 2762.12ms | 1325.78ms | 6.10ms |
| 통제 비교 후 | `5b4848c` | 적용 | 최적화 | 166.53 | 1223.27ms | 2028.40ms | 2511.86ms | 55.12ms | 5.46ms |

필터 적용 전 결과와 적용 후 리팩토링 전 결과 사이에서는 성공 TPS가 32.40% 낮고, API 평균 응답시간은 48.75% 높게 관찰됐습니다.

두 코드의 재고 차감 성공 경로에서 실질적인 변경은 소프트 삭제된 재고를 제외하는 `deleted_at IS NULL` 조건 추가입니다. 함께 반영된 마지막 재시도 후 backoff 제거는 모든 측정에서 락 타임아웃이 0건이었으므로 이번 결과에 영향을 주지 않았습니다.

다만 두 결과는 약 4시간 간격으로 서로 다른 실행 세션에서 측정됐습니다. 따라서 성능 차이가 관찰됐다는 사실은 기록하되, 전체 차이를 재고 삭제 필터의 영향으로 확정하지 않습니다. 락 구간 리팩토링의 공식 개선율은 재고 필터와 측정 조건을 동일하게 유지한 `e15ae40`과 `5b4848c`만 비교합니다. 재고 필터 자체의 성능 영향을 수치화하려면 동일한 세션에서 필터 적용 여부만 바꾼 대조 측정이 필요합니다.

## 해석

상품 조회와 응답 생성을 락 밖으로 이동하면서 평균 락 점유시간은 6.10ms에서 5.46ms로 감소했습니다. 동일 상품 요청이 직렬로 처리되는 구간이 짧아진 결과, 3회 중앙값 기준 성공 TPS는 9.85% 증가하고 API 평균 응답시간은 8.32% 감소했습니다.

평균 락 대기시간의 95.84% 감소를 API 성능 개선 폭과 동일하게 해석하면 안 됩니다. 상품 조회가 락 획득 전으로 이동하면서 요청이 DB 조회와 커넥션 풀을 통과한 뒤 락에 도달하므로, 기존에 Redis 락 앞에 형성되던 대기열 일부가 락 측정 구간 밖으로 이동했습니다. 실제 사용자 관점의 개선 폭은 API 응답시간과 TPS로 판단하고, 락 대기시간은 병목 위치가 바뀐 내부 지표로 해석합니다.

API p95 감소 폭 1.47%는 실행 간 편차보다 작으므로 독립적인 개선 근거로 강조하지 않습니다. 평균 응답시간, p99, TPS, 락 점유시간을 함께 제시합니다.

## 통계적 범위

한 번만 측정하면 그 순간의 CPU 사용량이나 DB 상태에 따라 결과가 크게 달라질 수 있습니다. 따라서 같은 조건에서 3번 측정하고, 각 지표의 세 결과 중 가운데 값을 대표값으로 사용했습니다. 유난히 높거나 낮은 결과 한 번의 영향을 줄이기 위한 방법입니다.

다만 3회 측정만으로 언제나 같은 개선 효과가 나온다고 증명할 수는 없습니다. 이 문서의 개선율은 동일한 로컬 환경에서 수행한 3회 측정 결과를 비교한 값입니다. 더 높은 신뢰도가 필요하면 개선 전과 후를 번갈아 실행하며 측정 횟수를 늘리고, 결과가 어느 범위에 분포하는지도 함께 계산해야 합니다.
