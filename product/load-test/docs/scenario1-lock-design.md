# 시나리오 1: 동일 상품 재고 차감 부하 테스트

- 관련 이슈: #5
- 대상 API: `PUT /v1/stocks`
- 부하 모델: Closed model (VU 고정)
- k6 executor: `constant-vus`
- 실행 모드: explore (웜업 → VU 20 → 50 → 100 → 200 탐색) / warmup (VU 10, 30초) / compare (지정 VU 본 측정)
- 시드 데이터: `seed/seed-scenario1-lock.sql`

---

## 왜 상품을 1개만 쓰는가

현재 재고 차감의 Redis 락 키는 다음과 같이 `productId` 단위로 생성됩니다.

~~~text
stock:decrease:{productId}
~~~

서로 다른 상품을 사용하면 요청마다 다른 Redis 락을 획득할 수 있습니다.

~~~text
상품 A 요청 → stock:decrease:A
상품 B 요청 → stock:decrease:B
~~~

이 경우 요청이 여러 락으로 분산되어 동일 상품에 대한 락 대기 현상이 약해집니다.

본 시나리오의 목적은 동일 상품에 대한 동시 요청이 하나의 Redis 락에 집중될 때의 성능을 확인하는 것입니다. 따라서 모든 VU가 동일한 `productId`로 재고 차감을 요청합니다.

여러 상품에 요청을 분산하는 테스트는 동일 락 경합의 영향을 구분하기 위한 비교 테스트가 필요할 때 별도 시나리오로 추가합니다.

## 왜 closed model인가

동일 상품에 대한 재고 차감 요청은 같은 Redis 락을 사용합니다.

한 요청이 락을 보유하고 있으면 다른 요청은 락을 획득할 때까지 기다리거나, 설정된 재시도 정책을 모두 소진한 후 실패합니다.

Open model에서 시스템의 최대 지속 처리량을 초과하는 요청률을 계속 유지하면 미처리 요청과 대기시간이 누적될 수 있습니다. 이 경우 측정된 응답시간이 테스트 지속 시간, 요청 타임아웃, VU 상한 등의 영향을
크게 받을 수 있습니다.

Closed model은 설정한 VU 수를 기준으로 동시 요청 수를 제한합니다. 이를 통해 VU를 단계적으로 증가시키면서 다음 변화를 관찰할 수 있습니다.

~~~text
동시 사용자 증가
→ 동일 Redis 락을 기다리는 요청 증가
→ 응답시간 및 실패율 변화
→ 성공 처리량의 증가 또는 포화
~~~

각 VU 단계에는 충분한 유지 시간을 설정하고, 해당 구간의 평균, p95, p99 응답시간과 성공 처리량을 비교합니다.

Closed model은 응답시간이 길어지면 각 VU의 다음 요청 생성 속도도 느려지는 특성이 있습니다. 따라서 결과를 해석할 때 VU 수뿐만 아니라 실제 요청률과 성공 처리량을 함께 확인합니다.

## 왜 초기 재고를 1억으로 잡았는가

웜업 (VU 10, 30초) 이후 VU 20 → 50 → 100 → 200 단계를 각 1분씩, 단계 사이 30초 간격을 두고 진행합니다.

재고가 테스트 도중 고갈되면 이후 요청은 "재고 부족" 예외로 락을 짧게 잡고 실패하는, 정상 차감과는 다른 코드 경로를 타게 되어 p95/p99가 오염됩니다.

1억은 예상 총 요청 수 대비 충분한 여유이자 INT 컬럼 최대값에서도 안전한 값입니다.

실제 테스트에서는 다음 조건도 확인합니다.

~~~text
초기 재고 > 예상 최대 성공 요청 수 × 요청당 차감 수량
~~~

최적화 전후 테스트 사이에는 시드 SQL을 다시 실행하여 초기 재고를 동일하게 복구합니다.

## 측정 지표

### k6 외부 지표

| 지표                  | k6 메트릭                          | 확인 목적                                             |
|-----------------------|------------------------------------|-------------------------------------------------------|
| 응답시간              | `http_req_duration`                | Redis 락 대기를 포함한 전체 API 응답시간 확인         |
| 평균 응답시간         | `avg`                              | 전체적인 응답시간 수준 확인                           |
| p95 응답시간          | `p(95)`                            | 전체 요청 중 느린 5% 구간의 영향 확인                 |
| p99 응답시간          | `p(99)`                            | 극단적으로 느린 요청과 긴 대기시간 확인               |
| 전체 요청률           | `http_reqs` rate                   | 초당 발생한 전체 HTTP 요청 수 확인                    |
| 시나리오 반복률       | `iterations` rate                  | 초당 완료된 k6 시나리오 반복 수 확인                  |
| 실패율                | `http_req_failed`                  | 예상하지 않은 HTTP 요청 실패 비율 확인                |
| 검증 성공률           | `checks`                           | 응답 상태와 응답 데이터가 예상 조건을 만족하는지 확인 |
| 락 타임아웃 실패 건수 | 커스텀 메트릭 (HTTP 409 응답 집계) | 락 대기 및 재시도 정책을 소진해 실패한 요청 수 확인   |

`dropped_iterations`는 사용하지 않습니다. 이 지표는 arrival-rate executor에서 VU가 부족하거나 iteration 기반 executor에서 `maxDuration`이 만료될 때
발생하는데, 본 시나리오의 `constant-vus`는 정해진 VU가 주어진 시간 동안 가능한 만큼 반복하므로 누락될 iteration 자체가 없습니다.

`http_reqs`에는 성공 요청과 실패 요청이 모두 포함될 수 있습니다. `setup`과 `teardown`에서 실행한 조회 요청도 집계 대상에 포함될 수 있습니다.

따라서 재고 차감의 성공 TPS는 HTTP 전체 요청률을 그대로 사용하지 않고, 차감에 성공한 요청만 별도 커스텀 메트릭으로 집계합니다.

실패 요청도 동일하게 두 가지로 분류하여 집계합니다. 락 타임아웃 (HTTP 409, `STOCK_LOCK_TIMEOUT`)은 락 정책이 의도한 실패이므로 경합 강도 지표로 사용하고, 그 외의 실패 (5xx,
네트워크 오류, 응답 검증 실패)는 테스트 신뢰성 문제로 별도 집계합니다.

**락 타임아웃 판별 가정**

- 이 엔드포인트에서 409를 반환하는 경로는 현재 `STOCK_LOCK_TIMEOUT` 뿐임을 코드로 확인했습니다 (`StockErrorCode`, Stock 도메인은 `GlobalException`만 사용).
- 에러 응답의 `code` 필드는 공통 라이브러리 `ErrorResponse.of()`가 값을 채우지 않아 현재 항상 null입니다. 따라서 스크립트는 409 + `success: false` 로 판별합니다.
- 공통 라이브러리 리팩토링으로 `code`가 채워지기 시작하면, 스크립트는 자동으로 `STOCK_LOCK_TIMEOUT` 코드 비교로 전환됩니다 (전방 호환 판별).

~~~text
성공 처리량
= 정상적으로 재고 차감이 완료된 요청 수 / 테스트 시간
~~~

**성공 TPS 계산 주의**

현재 사용하는 k6 v2.1.0의 end-of-test summary에서 Counter sub-metric의 `rate`는 개별 시나리오의 활성 시간이 아니라 전체 테스트 실행시간을 기준으로 계산됩니다.

따라서 여러 시나리오를 순차 실행하는 explore 모드에서는 `rate`를 해당 구간의 성공 TPS로 사용하지 않습니다.

~~~text
성공 TPS = 해당 시나리오의 성공 건수 / 해당 시나리오의 활성 시간(초)
~~~

같은 이유로 explore 모드에서는 `http_reqs`와 `iterations`의 `rate`도 각 VU 구간의 초당 처리량으로 해석하지 않습니다.

### 애플리케이션 내부 지표

Micrometer Timer로 계측하며 `loadtest` 프로필의 `/actuator/metrics`로 조회합니다.

| Timer             | 측정 구간                                      | 결과 태그                                     |
|-------------------|------------------------------------------------|-----------------------------------------------|
| `stock.lock.wait` | 첫 `tryLock()` 직전부터 획득·타임아웃·오류까지 | `acquired`, `timeout`, `interrupted`, `error` |
| `stock.lock.hold` | 락 획득 직후부터 `unlock()` 완료까지           | `success`, `error`, `ownership_lost`          |

`unlock()` 완료까지를 점유 구간에 포함하는 이유는, 대기 중인 다른 요청 입장에서는 Redis가 unlock을 처리할 때까지 락을 사용할 수 없기 때문입니다.

`ownership_lost`는 supplier 실행 후 `isHeldByCurrentThread()`가 `false`인 경우입니다. `leaseTime` 초과로 락이 자동 해제되었거나 그 밖의 이유로 소유권을 잃은
상태이며, 다른 요청이 이미 임계 구역에 진입했을 수 있는 정합성 위험 신호입니다. 계측 단계에서는 기록만 하고 예외를 새로 던지지 않습니다.

현재 락 획득 로직은 한 번의 `waitTime`만 적용하는 것이 아니라 제한된 횟수만큼 재시도합니다.

따라서 락 타임아웃을 단순히 “3초 안에 락을 획득하지 못한 요청”이라고 표현하지 않고, “설정된 락 대기 및 재시도 정책을 모두 소진한 요청”으로 정의합니다. 락 타임아웃 건수는 k6의 409 집계와 교차 검증하여
측정 신뢰성을 확인합니다.

**이번 측정 범위에서 제외한 것**

- 락 획득 재시도 횟수: 재시도가 늘어나는 상황은 대기 시간 증가로 `stock.lock.wait`에 이미 반영되므로 별도 Counter를 두지 않습니다.
- 락 시간의 p95/p99: `/actuator/metrics`는 Timer의 measurement로 `COUNT`, `TOTAL_TIME`, `MAX` 세 가지만 노출합니다. `publishPercentiles`
  를 설정하더라도 이 엔드포인트 응답에는 백분위가 포함되지 않습니다. 백분위를 외부에서 조회하려면 Prometheus 같은 레지스트리 익스포터를 도입하거나 Timer snapshot을 읽는 별도 엔드포인트를
  만들어야 하며, 둘 다 이번 측정 범위를 넘습니다. 따라서 락 구간은 평균으로 비교하고, 백분위는 k6가 측정하는 API 응답시간으로 확인합니다.

## 측정 절차와 계산 방법

Micrometer Timer는 애플리케이션 시작 이후 값을 누적합니다. 웜업 구간과 본 측정 구간이 하나의 Timer에 합산되므로, 본 측정 구간만 분리하려면 스냅샷 차분이 필요합니다.

~~~text
product 서비스 재시작
→ 시드 초기화
→ warmup 실행 (VU 10, 30초)
→ 스냅샷 A
→ compare 실행 (VU 200, 60초)
→ 서버 측 요청 처리 완료 대기
→ 스냅샷 B
~~~

k6가 종료해도 서버는 락을 기다리거나 임계 구역을 실행하는 중일 수 있습니다. 그 상태로 스냅샷 B를 저장하면 일부 요청의 Timer 기록이 빠지므로, 처리가 끝난 뒤에 저장합니다.

compare 모드는 웜업을 포함하지 않고 `startTime: '0s'`부터 본 측정만 수행합니다. 웜업은 별도 실행이지만 같은 서버 프로세스를 유지하므로 예열 효과는 그대로 남습니다.

**평균 계산**

Actuator가 반환하는 `TOTAL_TIME`은 Timer의 기본 단위인 **초**입니다. ms로 기록하려면 1,000을 곱합니다.

~~~text
평균 락 대기시간(ms)
= (acquired의 (B.totalTime - A.totalTime) / (B.count - A.count)) × 1000

평균 락 점유시간(ms)
= (success의 (B.totalTime - A.totalTime) / (B.count - A.count)) × 1000
~~~

단위는 Actuator 응답의 `baseUnit` 필드로 확인합니다. 이 값이 `seconds`가 아니면 1,000배 틀린 값이 기록되므로 계산 전에 반드시 확인합니다.

MAX는 합계가 아니라 최근 측정 구간에서 가장 오래 걸린 단일 요청 시간입니다. 따라서 B.MAX - A.MAX 방식으로 본 측정 구간의 최대시간을 계산할 수 없습니다.

또한 스냅샷 B의 MAX에는 warmup 결과가 남아 있을 수 있으므로 이상치 확인을 위한 참고값으로만 사용하고 공식 전후 비교에서는 제외합니다.

**대표값**

유효한 측정 3회에서 **지표별로 독립적인 중앙값**을 사용합니다. 원본 3회 결과도 함께 기록합니다.

## 측정 유효성 기준

**교차 검증**

~~~text
wait acquired 증가량
= hold success + hold error + hold ownership_lost 증가량
→ 락을 획득한 요청마다 점유 결과가 정확히 하나 있어야 하는 내부 불변식

hold success 증가량
= k6 stock_decrease_successes{scenario:compare}
→ 항상 성립하는 항등식은 아님. 락 해제 이후 응답 직렬화·네트워크·k6 요청 타임아웃
   구간에서 어긋날 수 있으므로, 불일치 시 계측 오류로 단정하지 않고 원인을 조사

wait timeout 증가량
= k6 stock_lock_timeouts{scenario:compare}
→ 양쪽 모두 0이면 통과이지만 증명력은 없음
~~~

k6 결과를 읽을 때는 전역 지표가 아니라 반드시 `{scenario:compare}` 태그가 붙은 sub-metric을 사용합니다. `setup`과 `teardown`의 재고 조회 요청이 전역 지표에 섞이기
때문입니다.

**유효 조건**

~~~text
wait error = 0
wait interrupted = 0
hold error = 0
hold ownership_lost = 0
k6 unexpected failure = 0
측정 구간에 락 획득이 1건 이상 존재
스냅샷 A와 B가 동일한 서버 프로세스에서 수집됨
~~~

**위반 시 처리**

| 항목                                              | 처리                                                                                  |
|---------------------------------------------------|---------------------------------------------------------------------------------------|
| `wait error`, `wait interrupted`, `k6 unexpected` | 결과 보존 → 원인 제거 → 동일 RUN 번호로 재측정                                        |
| `hold error`                                      | 결과 보존 → 원인 확인 후 판단                                                         |
| `hold ownership_lost`                             | **baseline 수집 중단** → lease 정책 분석 → 별도 커밋으로 수정 → 3회를 처음부터 재측정 |

`ownership_lost`가 발생한 실행만 골라 제외하고 정상 실행으로 3회를 채우면 선택 편향이 생깁니다. 발생 자체가 정합성 위험 신호이므로 수집을 멈추고 원인을 먼저 해결합니다.

`leaseTime` 등 락 정책을 변경한 경우, 리팩토링 전후 측정에 **동일한 값**이 적용되어야 합니다. 비교에서 달라지는 변수는 락 스코프 리팩토링뿐이어야 하므로, 정책 값은 매 측정의 메타 정보에
기록합니다.

모든 측정 시도는 삭제하지 않고 결과 파일과 제외 사유를 함께 보존합니다.

## 재고 정합성 검증

성능 개선 후에도 재고 정합성이 유지되어야 합니다.

테스트 종료 후 다음 조건을 검증합니다.

~~~text
전체 요청 수
= 성공 요청 수
+ 정책상 허용된 실패 요청 수
+ 예상하지 않은 실패 요청 수
~~~

~~~text
최종 재고
= 초기 재고 - (성공 요청 수 × 요청당 차감 수량)
~~~

~~~text
최종 재고 >= 0
~~~

락 타임아웃이 정책상 허용되는 경우, 실패한 요청은 재고 차감 성공 건수에 포함하지 않습니다.

예상하지 않은 `5xx`, 네트워크 오류 또는 응답 검증 실패는 별도로 집계합니다.

## UUID 저장 형식

UUID 컬럼은 `BINARY(16)`이므로 `UUID_TO_BIN()`으로 변환하여 저장합니다.
