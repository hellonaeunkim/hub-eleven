# 시나리오 1: 동일 상품 재고 차감 부하 테스트

- 관련 이슈: #5
- 대상 API: `PUT /v1/stocks`
- 부하 모델: Closed model (VU 고정)
- k6 executor: `ramping-vus`
- 시드 데이터: `seed/seed-scenario1-lock.sql`

---

## 왜 상품을 1개만 쓰는가

현재 재고 차감의 Redis 락 키는 다음과 같이 `productId` 단위로 생성됩니다.

~~~text
stock:decrease:{productId}
~~~

서로 다른 상품을 사용하면 요청마다 다른 Redis 락을 획득할 수 있습니다.

~~~text
상품 A 요청 → stock:decrease:A
상품 B 요청 → stock:decrease:B
~~~

이 경우 요청이 여러 락으로 분산되어 동일 상품에 대한 락 대기 현상이 약해집니다.

본 시나리오의 목적은 동일 상품에 대한 동시 요청이 하나의 Redis 락에 집중될 때의 성능을 확인하는 것입니다. 따라서 모든 VU가 동일한 `productId`로 재고 차감을 요청합니다.

여러 상품에 요청을 분산하는 테스트는 동일 락 경합의 영향을 구분하기 위한 비교 테스트가 필요할 때 별도 시나리오로 추가합니다.

## 왜 closed model인가

동일 상품에 대한 재고 차감 요청은 같은 Redis 락을 사용합니다.

한 요청이 락을 보유하고 있으면 다른 요청은 락을 획득할 때까지 기다리거나, 설정된 재시도 정책을 모두 소진한 후 실패합니다.

Open model에서 시스템의 최대 지속 처리량을 초과하는 요청률을 계속 유지하면 미처리 요청과 대기시간이 누적될 수 있습니다. 이 경우 측정된 응답시간이 테스트 지속 시간, 요청 타임아웃, VU 상한 등의 영향을
크게 받을 수 있습니다.

Closed model은 설정한 VU 수를 기준으로 동시 요청 수를 제한합니다. 이를 통해 VU를 단계적으로 증가시키면서 다음 변화를 관찰할 수 있습니다.

~~~text
동시 사용자 증가
→ 동일 Redis 락을 기다리는 요청 증가
→ 응답시간 및 실패율 변화
→ 성공 처리량의 증가 또는 포화
~~~

각 VU 단계에는 충분한 유지 시간을 설정하고, 해당 구간의 평균, p95, p99 응답시간과 성공 처리량을 비교합니다.

Closed model은 응답시간이 길어지면 각 VU의 다음 요청 생성 속도도 느려지는 특성이 있습니다. 따라서 결과를 해석할 때 VU 수뿐만 아니라 실제 요청률과 성공 처리량을 함께 확인합니다.

## 왜 초기 재고를 1억으로 잡았는가

VU 20 → 50 → 100 → 200 단계를 각각 램프업 + 유지 구간으로 몇 분간 진행합니다.

재고가 테스트 도중 고갈되면 이후 요청은 "재고 부족" 예외로 락을 짧게 잡고 실패하는, 정상 차감과는 다른 코드 경로를 타게 되어 p95/p99가 오염됩니다.

1억은 예상 총 요청 수 대비 충분한 여유이자 INT 컬럼 최대값에서도 안전한 값입니다.

실제 테스트에서는 다음 조건도 확인합니다.

~~~text
초기 재고 > 예상 최대 성공 요청 수 × 요청당 차감 수량
~~~

최적화 전후 테스트 사이에는 시드 SQL을 다시 실행하여 초기 재고를 동일하게 복구합니다.

## 측정 지표

### k6 외부 지표

| 지표       | k6 메트릭               | 확인 목적                          |
|----------|----------------------|--------------------------------|
| 응답시간     | `http_req_duration`  | Redis 락 대기를 포함한 전체 API 응답시간 확인 |
| 평균 응답시간  | `avg`                | 전체적인 응답시간 수준 확인                |
| p95 응답시간 | `p(95)`              | 전체 요청 중 느린 5% 구간의 영향 확인        |
| p99 응답시간 | `p(99)`              | 극단적으로 느린 요청과 긴 대기시간 확인         |
| 전체 요청률   | `http_reqs` rate     | 초당 발생한 전체 HTTP 요청 수 확인         |
| 시나리오 반복률 | `iterations` rate    | 초당 완료된 k6 시나리오 반복 수 확인         |
| 실패율      | `http_req_failed`    | 예상하지 않은 HTTP 요청 실패 비율 확인       |
| 검증 성공률   | `checks`             | 응답 상태와 응답 데이터가 예상 조건을 만족하는지 확인 |
| 누락 반복 수  | `dropped_iterations` | 설정한 부하를 생성하지 못한 반복이 있는지 확인     |
| 락 타임아웃 실패 건수 | 커스텀 메트릭 (HTTP 409 응답 집계) | 락 대기 및 재시도 정책을 소진해 실패한 요청 수 확인 |

`http_reqs`에는 성공 요청과 실패 요청이 모두 포함될 수 있습니다. `setup`과 `teardown`에서 실행한 조회 요청도 집계 대상에 포함될 수 있습니다.

따라서 재고 차감의 성공 TPS는 HTTP 전체 요청률을 그대로 사용하지 않고, 차감에 성공한 요청만 별도 커스텀 메트릭으로 집계합니다.

실패 요청도 동일하게 두 가지로 분류하여 집계합니다. 락 타임아웃(HTTP 409, `STOCK_LOCK_TIMEOUT`)은 락 정책이 의도한 실패이므로 경합 강도 지표로 사용하고, 그 외의 실패(5xx, 네트워크 오류, 응답 검증 실패)는 테스트 신뢰성 문제로 별도 집계합니다.

**락 타임아웃 판별 가정**

- 이 엔드포인트에서 409를 반환하는 경로는 현재 `STOCK_LOCK_TIMEOUT` 뿐임을 코드로 확인했습니다 (`StockErrorCode`, Stock 도메인은 `GlobalException`만 사용).
- 에러 응답의 `code` 필드는 공통 라이브러리 `ErrorResponse.of()`가 값을 채우지 않아 현재 항상 null입니다. 따라서 스크립트는 409 + `success: false` 로 판별합니다.
- 공통 라이브러리 리팩토링으로 `code`가 채워지기 시작하면, 스크립트는 자동으로 `STOCK_LOCK_TIMEOUT` 코드 비교로 전환됩니다 (전방 호환 판별).

~~~text
성공 처리량
= 정상적으로 재고 차감이 완료된 요청 수 / 테스트 시간
~~~

### 애플리케이션 내부 지표

| 지표          | 측정 구간                       | 확인 목적                       |
|-------------|-----------------------------|-----------------------------|
| 락 대기시간      | `tryLock` 호출 직전부터 락 획득 성공까지 | 요청이 Redis 락을 기다린 시간 확인      |
| 락 점유시간      | 락 획득 성공부터 `unlock` 직전까지     | 락 내부 작업이 Redis 락을 보유한 시간 확인 |
| 락 획득 재시도 횟수 | 최초 락 획득 시도부터 성공 또는 실패까지     | 동시 요청 증가에 따른 경합 정도 확인       |
| 락 타임아웃 건수   | 모든 락 획득 시도를 소진한 요청 수        | 설정된 락 정책으로 처리하지 못한 요청 수 확인. k6의 409 집계와 교차 검증하여 측정 신뢰성 확인 |

현재 락 획득 로직은 한 번의 `waitTime`만 적용하는 것이 아니라 제한된 횟수만큼 재시도합니다.

따라서 락 타임아웃을 단순히 “3초 안에 락을 획득하지 못한 요청”이라고 표현하지 않고, “설정된 락 대기 및 재시도 정책을 모두 소진한 요청”으로 정의합니다.

## 재고 정합성 검증

성능 개선 후에도 재고 정합성이 유지되어야 합니다.

테스트 종료 후 다음 조건을 검증합니다.

~~~text
전체 요청 수
= 성공 요청 수
+ 정책상 허용된 실패 요청 수
+ 예상하지 않은 실패 요청 수
~~~

~~~text
최종 재고
= 초기 재고 - (성공 요청 수 × 요청당 차감 수량)
~~~

~~~text
최종 재고 >= 0
~~~

락 타임아웃이 정책상 허용되는 경우, 실패한 요청은 재고 차감 성공 건수에 포함하지 않습니다.

예상하지 않은 `5xx`, 네트워크 오류 또는 응답 검증 실패는 별도로 집계합니다.
